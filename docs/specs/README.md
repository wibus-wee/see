# Implementation-Agnostic Specifications 索引

这组规格把参考项目中可迁移的能力拆成独立、可验证的行为契约。每份规格都面向**尚未接触参考项目的实现者**：只描述外部行为、关键机制、状态流转、不变量、边界条件和验收方法，不要求复刻原项目的语言、包结构、trait/interface、依赖或线程模型。

## 规格列表

| 编号 | 规格 | 独立复现的能力 |
| --- | --- | --- |
| SPEC-000 | [需求 conformance 与行为等价验证框架](00-verification-framework.md) | 用需求覆盖率和真实行为证明实现正确，而不是用类型检查或单元测试冒充完成 |
| SPEC-001 | [能力协商与功能降级](01-capability-negotiation.md) | 显式表达能力、按功能门控、能力缺失时安全降级 |
| SPEC-002 | [不可变组合与操作策略管线](02-composable-operation-policies.md) | 在不改业务适配器的情况下组合超时、日志、限流、重试、故障注入等策略 |
| SPEC-003 | [事务式写入生命周期](03-transactional-write-lifecycle.md) | 写入、提交、中止、崩溃恢复和并发冲突的可观察语义 |

## 如何使用

1. 先读 SPEC-000，建立验收方式和证据标准。
2. 按目标系统需要选择规格，不要求一次实现全部。
3. 对每条 normative requirement 建立需求追踪记录：`需求 ID -> 用户流程/接口 -> 实现位置 -> 行为证据 -> 状态`。
4. 验收必须从真实用户流程或真实外部边界出发；单元测试只能作为补充证据。
5. 如果目标系统架构不同，优先保留“本质机制”，替换“实现选择”。每份规格都明确区分二者。

## 通用术语

- **MUST / MUST NOT**：不实现即不符合规格。
- **SHOULD / SHOULD NOT**：有充分理由才能偏离；偏离必须记录并验证风险。
- **MAY**：实现者可选，不影响符合性。
- **外部可观察行为**：用户、调用方、文件系统、进程、网络服务或日志能观察到的结果。
- **真实行为证据**：运行系统得到的录屏、日志、文件状态、进程状态、网络交互或行为测试输出。
- **参考行为**：参考项目在外部边界上表现出的行为，不是其内部类名、模块名或依赖。

## 不符合规格的证据

以下证据不能单独证明需求已实现：

- 编译、lint、类型检查通过；
- 单元测试或 mock 测试通过；
- 代码中存在同名类型、函数、目录或接口；
- 理论上可以工作；
- 覆盖率百分比；
- 开发者口头说明。

这些只能作为辅助证据。最终状态必须来自真实行为验收和需求追踪矩阵。
