# Lane C: transactional writes and versioned configuration

Baseline: See `bbccc32` (identical in code to `specs-opendal-dispatch` / `f3d214c`, which adds only spec documents). Evaluation: the revision containing this report on `spec-lane-c-writes`, Darwin arm64, Go 1.27.4. Baseline locations below refer to `git show bbccc32:<path>`, not current line numbers. Status follows [SPEC-000](../00-verification-framework.md): **implemented** means observed at the stated boundary; **partial** names the remaining limitation. These are requirement counts, not line coverage.

The evaluated paths are editor save (`saveDoc`), untitled save-as, workspace search-edit writes, LSP code-action file writes (`applyEditsToFile`), configuration load/validate/write-back (`internal/config`), and the write primitive they now share ([internal/atomicfile](../../../internal/atomicfile/atomicfile.go)). Already-transactional writers outside this lane — `internal/search/replace.go` (hashed staging replace), `internal/git/conflict.go` (merge resolution), `internal/localhistory` (local history snapshots), the recovery cache in `internal/app/recovery.go`, and the staging-directory installs in `internal/app/tools.go` and `internal/languages/install.go` — were re-verified by their existing suites but not modified. The avatar cache (`internal/avatar/avatar.go:90`) writes user caches non-atomically; it is a display cache, not user content, and out of the lane's file ownership, so it is documented here rather than changed.

Reference: Apache OpenDAL `c0ce8b66` (current layout: `core/core/src/...`). The multipart lifecycle — write accepts parts, only `complete` publishes, `abort` discards staging and ends the session, and a failed publish never exposes staging as the object — informed the session design. The mapping is semantic, not structural: See's target is a local file, the "upload id" is a same-directory staging file, and publish is a rename. The fs-service behavior (fsync and metadata applied on staging before rename, staging removed on failure, the old target preserved) matches what `atomicfile` implements.

## The write lifecycle primitive

`internal/atomicfile` is the new package every evaluated path now shares. One `Session` is one logical overwrite: `Write` buffers into the staging file, `Commit` syncs, closes and publishes it by rename, `Abort` discards it. Key deviations from the spec's literal recommendations are documented per-requirement below.

| Requirement | Baseline status and evidence | Evaluated status | Call, observation and remaining limits |
|---|---|---|---|
| REQ-WR-010 | partial: `editing.go` `saveDoc` returned bool after `os.WriteFile` completed, so completion existed in practice, but nothing distinguished accepted bytes from published bytes: one truncate-write conflated both | implemented | `Session.Write` is an `io.Writer` (acceptance only); only a nil `Commit` means the bytes are the target's. `TestCommitFailureDoesNotReportSuccess` fails the publish and observes the error. `WriteFile` documents the all-or-nothing contract. |
| REQ-WR-020 | missing: `os.WriteFile` partial writes invisible to callers | implemented | `atomicfile.WriteFile` is all-or-nothing by construction; `TestWriteFilePublishesExactBytesAndKeepsMode` streams 100 KiB in 997-byte pieces and observes byte-identity. The `io.Writer` contract of `Session.Write` (a prefix may be accepted with the error) is documented. |
| REQ-WR-030 | partial: `saveDoc` did propagate the `os.WriteFile` error — but only after having already truncated the file. `config.Save` propagated rename errors | implemented | `Commit` reports sync/close/rename failure and never swallows it; cleanup failures deliberately cannot mask an already-reported error (documented in `Abort`). `TestCommitFailureDoesNotReportSuccess`, and harness `TestSaveFailureReportsErrorAndKeepsOldBytes` which observes the error note in the real UI state. |
| REQ-WR-040 | missing: no session concept existed | implemented | Documented poisoned semantics: after a write error or after Commit/Abort, all further `Write`/`Commit` fail on that session; the retry is a fresh session writing everything again. Asserted in `TestCommitFailureDoesNotReportSuccess`. The threading contract is explicit and enforced: one session may be shared across goroutines — `Write`, `Commit` and `Abort` serialize on a mutex, and the first `Commit` or `Abort` to arrive ends the session for the rest (`TestSessionSharedAcrossGoroutines`, race-clean). What the caller still owns is ordering: which write lands before a racing commit is their synchronization, as with `os.File`. |
| REQ-WR-050 | missing: `config.Save` left `config.json.tmp` behind on any write failure; crashed saves left nothing distinguishable | implemented | `Abort` and failed `Commit` remove the staging file. Orphaned staging after a real crash is documented as caller-owned debris (see REQ-WR-100). `TestWriteFileFailureKeepsOldBytesAndNoStaging`, `TestAbortExposesNothing`. |
| REQ-WR-060 | missing: `saveDoc` wrote with `os.WriteFile` (truncate in place); `applyEditsToFile` the same. `writeFileAtomically` did stage, fsync and rename — but served only untitled save-as and search edits, so the two writes users make most bypassed it entirely | implemented | All four save/write paths now publish through same-directory staging + fsync + rename. `TestSaveFailureReportsErrorAndKeepsOldBytes` (harness, real editor save), `TestAtomicWriteFailureLeavesNoPartialDestination` (save-as), config `TestSaveLeavesNoStagingBehind`. Directory fsync after the rename is deliberately omitted: the rename is atomic in the directory entry, and the window it would close is the same-machine-crash durability of the directory entry itself, which the spec leaves to the implementation. |
| REQ-WR-070 | partial: `saveDoc` checked disk contents against the last-read text before writing, and `internal/search` enforces hash matches in its own rename-boundary protocol | partial | The conflict check still runs before the write begins, because POSIX rename carries no condition: an external write landing between the check and the rename is silently overwritten, and the window is the entire staging write — measured at milliseconds for small files, growing with file size and network volume latency — not a microsecond race at the rename. Documented in the `atomicfile` package comment. `TestRecoveredEditsRefuseToOverwriteExternalChanges` covers the check itself (refusal, then explicit Overwrite). `internal/search/replace.go` already enforces staleness inside its transaction via line hashes and `SameFile` — its `TestReplaceRejectsStaleMatchWithoutPartialWrite` passes unmodified. `atomicfile` now offers the two conditional-publish shapes POSIX allows, for the file-observation integration to wire: `CommitIf(cond)` evaluates after staging is durable and closed, immediately before the rename — best-effort, shrinking the window to the rename boundary, the REQ-COND-070-documented degradation — and `CommitIfAbsent` publishes through a hard link, the one conditional publish the kernel makes truly atomic (`TestCommitIfEvaluatesAtThePublishBoundary`, `TestCommitIfAbsentIsAtomicUnderConcurrency`). Neither closes the overwrite window for existing files: that would need file locking protocols the platforms do not offer for regular files. |
| REQ-WR-080 | missing: no staging existed to retain or clean | divergent | Documented deviation from the SHOULD: publish failures always clean staging rather than retaining it for in-place retry. The reasoning was corrected in independent verification — the original premise, that rename failures are permanent configuration failures, is factually false: NFS and FUSE renames fail with ESTALE from client cache races, signals interrupt them with EINTR, soft mounts return EIO while a server is down, and retrying the identical rename is the documented remedy for several of these. The deviation survives for the reasons that hold: after EINTR or a network filesystem error the rename may already have happened server-side, so the publish state is the spec's Uncertain — safe republishing is only possible when the failure is known to predate the rename, which the error alone cannot tell — and every caller regenerates the staged bytes at no cost (editor buffers, serialized settings), so retention buys nothing even when a retry was safe. The hazard matters if the primitive is ever reused for non-regenerable bytes; the Commit comment now warns that such callers must stream again from their source. The isolation half is implemented and tested: random per-session names make cross-session reuse impossible (`TestCrashLeavesOldBytesAndStagingImpersonatesNothing`). |
| REQ-WR-090 | missing: two concurrent truncating writes interleaved silently | implemented | Documented last-writer-wins: `TestConcurrentWritesNeverInterleave` runs 2×20 overlapping writes and asserts the target always holds one complete version, never a mix. |
| REQ-WR-100 | partial: crash recovery existed for unsaved editor text (`.see/recovery`, tested in `persistence_behavior_test.go`) and passes unmodified; but a crash mid-save corrupted the target file itself | implemented | `TestCrashLeavesOldBytesAndStagingImpersonatesNothing` kills a helper process with an uncommitted staged write (kill -9 after a readiness signal): the target holds the old bytes, the orphaned staging file is never mistaken for the target, and a fresh write succeeds. Visibility semantics documented in the package comment: orphans are dot-hidden, caller-owned, safe to inspect or delete, never auto-removed (they may hold the only copy of uncommitted work). The editor-level recovery suite (`TestRecoveredEditsRefuseToOverwriteExternalChanges`, `TestUntitledSaveKeepsEditsMadeBeforeCompletion`) passes unmodified. |
| REQ-WR-110 | partial: BOM and line endings were already caller-preserved byte content (BOM tests in the save suite pass unmodified); mode was preserved by `writeFileAtomically` but not by `saveDoc` | partial | `Begin` preserves the replaced file's permission bits (`TestWriteFilePublishesExactBytesAndKeepsMode`); BOM/line-endings remain caller-level byte content, unchanged. Remaining limitations, now documented rather than accidental: hard-linked files lose their link (the write replaces the directory entry instead of truncating the shared inode — the standard atomic-save trade-off); extended attributes and ACLs of the replaced file do not survive replacement; setuid, setgid and sticky bits are stripped because only `Perm()` bits are copied; a dangling symlink is replaced rather than followed. mtime updates are the semantic content of a save. Configuration files keep their existing mode on overwrite (an 0640 `config.json` stays 0640 — verified, correcting the verification report's 0640→0600 claim); the 0600 of `WriteFilePerm` applies only to newly created files. None of these regress the baseline: direct truncation preserved xattrs/hardlinks only by accident of implementation, and the baseline corrupted content instead. |

### Symlink behavior, contrasted

Two writers deliberately differ, and the matrix records both: editor saves follow symlinks (the write lands on the resolved target, matching the baseline behavior and every other editor), while workspace replace (`internal/search`) refuses symlinked files outright — `TestReplaceDoesNotFollowSymlinkOrOverwriteReadOnlyFile` passes unmodified.

## Versioned configuration

`internal/config` was rewritten around the contract: [load pipeline](../../../internal/config/config.go), [issue categories](../../../internal/config/issues.go), [behavior tests](../../../internal/config/contract_test.go). The write-back half is REQ-WR-060 territory and shares `atomicfile`.

| Requirement | Baseline status and evidence | Evaluated status | Call, observation and remaining limits |
|---|---|---|---|
| REQ-CFG-010 | partial: the Go struct was a de-facto schema with types, defaults and doc comments, but nothing validated it and unknown keys were silently dropped on write-back | implemented | The struct remains the explicit contract — field names, types, defaults and domains documented per field — now enforced by a per-field decode against it. Free-form extension keys have a documented preserve-and-write-back policy (`TestUnknownKeysSurviveRoundTrip`). |
| REQ-CFG-020 | missing: no version field, no migration story | implemented | `CurrentVersion = 1`; every written file declares `"version": 1` (`TestSavedConfigurationDeclaresVersion`). Unversioned files are schema 0, read identically — documented at the constant. A newer version degrades with a `version_newer` issue while known keys still load, unknown keys survive, and write-back keeps the newer version declaration rather than silently downgrading it (`TestNewerVersionDegradesWithIssue`). |
| REQ-CFG-030 | missing: one `json.Unmarshal` collapsed every phase into success-or-reset | implemented | Phases now exist and report distinct categories: `read_failed` (not found is the first run, no issue), `parse_failed`, `schema_invalid`, `validation_failed`, `version_newer` ([issues.go](../../../internal/config/issues.go)). `migration failed` and `source conflict` have no producing phase — no migration and no second source exist — which the matrix records rather than invents. Each is test-observed: `TestUnreadableFileReportsReadFailure`, `TestSyntaxCorruptionKeepsOriginalBacksUpAndDegrades`, `TestSchemaInvalidFieldDegradesOnlyThatKey`, `TestEditorFontSizeOutOfRangeDegrades` (the validation-failure behavior evidence — the pre-fix `TestValidationFailurePreservesOriginalOnWriteBack` this cell once cited was inverted by the fix round and no longer exists). |
| REQ-CFG-040 | missing: `json.Unmarshal` failure reset everything to defaults **in memory while keeping the save path** — the next settings change would overwrite the user's broken file, destroying it without backup or notice | implemented | The original file is never modified; a backup copy is written before anything else can happen (`config.json.broken-<timestamp>`); the load degrades to defaults with a `parse_failed` issue carrying the backup path; startup surfaces it on the welcome screen and in the log (`TestConfigLoadNoteSurfacesCorruption` observes the note, the backup bytes and the untouched original in one scenario). The overwrite gate is enforced on the failure path, closing the hole independent verification found: when the backup write itself fails, the original is the only copy of what the user had, so `Save` completes the backup first and refuses — changing nothing — while even that fails (`TestFailedBackupBlocksOverwriteUntilBackupSucceeds`, including the transient case: a full disk or permission problem at launch that has since been fixed heals on the first save, backup then overwrite, never unprotected in between). JSON syntax errors carry no position detail beyond what `encoding/json` reports, which is what the issue quotes. |
| REQ-CFG-050 | implemented: single source — no CLI flags or environment variables override settings (`internal/cli` has open-path arguments only); documented absence of a precedence question | implemented | Verified by inspection of `internal/cli` and `main.go`: the user configuration file is the only source, so precedence is trivially fixed. Recorded here because a future second source must design precedence explicitly. |
| REQ-CFG-060 | partial: ranges were clamped at use time (`EditorFontSize()` and siblings), silently — no error, no bounded-degradation contract, enums fell through switch defaults unnoticed | implemented | Enums and contractual ranges now produce `validation_failed` issues at load: the field keeps its default in memory, write-back converges the key to that in-memory truth (the representability contract of REQ-CFG-070 — a validation failure is representable, so it does not survive write-back), and the startup note names it (`TestEditorFontSizeOutOfRangeDegrades`, `TestValidationFailureConvergesToInMemoryTruthOnWriteBack`). Validated domains: `appearance`, `inspectorTab`, `terminalCursor`, `terminalRightClick`, `terminalClipboard`, `parameterHelp`, `diffLayout`, `editorFontSize`, `terminalFontSize`, `editorLineNumbers`, `editorPageGuideColumn`, `panelPercent`, `terminalLineHeight`. Fields outside this list — scroll sensitivities, font weights, free-form font families — are read only through consumers that clamp or ignore what they do not understand, which is their documented bounded degradation. The contract is per-field: a field in the validated list degrades alone; the file as a whole never fails to load. |
| REQ-CFG-070 | missing: unknown keys were dropped on write-back; a downgrade-upgrade round trip lost everything the newer build had written | implemented | Write-back decides per key by what memory can represent, after independent verification refuted blanket preservation. Preserved verbatim: keys this build does not know, values that do not fit their key's type (`TestSchemaInvalidValueStaysPreservedOnWriteBack`), and a version declaration that is not a number (`TestWronglyTypedVersionStaysPreservedOnWriteBack`). One exception the re-verification pinned (`TestReverifyHiddenNamesTypeMismatchCollision`): `hiddenNames` is the struct's only non-omitempty field, so it always emits into the marshaled map and wins every collision — a type-mismatched `"hiddenNames": 42` is overwritten with the default on the first save rather than preserved verbatim. The convergence direction is the desirable one for a corrupted value, but it is an exception to the blanket rule, recorded here because the blanket claim is false without it. Not preserved — the explicit overwrite scope this requirement permits, documented at `MarshalJSON`: values that fit their type but fail validation. They are representable in memory, so the file converges to the in-memory truth — the degraded default or the user's later choice (`TestValidationFailureConvergesToInMemoryTruthOnWriteBack`). The convergence is forced by the zero-value repair the blanket rule made impossible: a repair to the default emits no key (every field is omitempty), so the preserved invalid value won the write-back back, the file could never heal, and the warning repeated forever while the settings already showed the intended state (`TestZeroValueResetSticksOnWriteBack`); no state can distinguish that repair from a field never touched, so nothing weaker can work. The accepted cost: downgrading across an enum widened by a newer build replaces the newer value with the in-memory truth on the first save — bounded, never destructive of in-effect settings, and preserved unknown keys remain the primary downgrade protection. Two documented normalizations: indentation inside preserved values follows the file's formatting (values are byte-semantics-identical), and explicit `null` reads as unset and is omitted on write-back, which carries the same information (`TestNullReadsAsDefaultAndNormalizesOnWriteBack`). |
| REQ-CFG-080 | partial: the configuration is user-owned only; no project-level or workspace-shipped configuration exists, so no untrusted input reaches it — this boundary was never documented | implemented | Verified by inspection: there is no project configuration file mechanism in the repository, so the trust boundary is the user owning their own `config.json`, which needs no validation against itself. Security-relevant fields that do exist (`terminalShell`, `terminalEnv`, `lsp` command arrays) execute with the user's own authority by design — the same authority the user has in their shell. Documented here as the standing contract: any future project-level configuration must treat these fields as untrusted, as SPEC-007 says. |
| REQ-CFG-090 | partial: single snapshot at startup, mutated only on the UI goroutine, never reloaded — true but undocumented | implemented | Documented contract: the configuration loads once at startup into one snapshot; settings changes mutate it on the main goroutine and write back through `Save`; nothing reloads mid-run, so no operation can observe a half-old-half-new combination. External edits to the file while See runs are picked up at the next launch, and a Save in the meantime overwrites them — recorded as the known limitation of the snapshot model. |
| REQ-CFG-100 | missing: no migrations exist | implemented | No breaking schema change has ever occurred, so there is no migration to test or roll back — recorded rather than invented. The contract for the first breaking change is written at `CurrentVersion`: raise the version, write a backup before touching the file, and only then rewrite it. The backup machinery exists and is tested today on the parse-failure path (`TestSyntaxCorruptionKeepsOriginalBacksUpAndDegrades`), and unknown-key preservation means a downgrade never destroys newer data — the rollback path that matters most. |

### The write-back transaction

`Save` now stages through `atomicfile` with mode 0600 for new files: `TestFailedSavePreservesPreviousSettingsAndCanRetry` blocks the parent directory with a plain file (portably, no permission games) and observes the committed file byte-identical afterwards, no leaked settings, and a successful retry; `TestSaveLeavesNoStagingBehind` checks the directory after success. The baseline's fixed `config.json.tmp` staging name — where two concurrent writers or a leftover from a crash could collide or be mistaken for in-progress state — is replaced by per-session random names.

## Known gaps, restated

1. Conflict detection before publish is best-effort: an external write in the check-to-rename window is silently overwritten (REQ-WR-070), and the window spans the entire staging write, growing with file size. `CommitIf` shrinks it to the rename boundary once the file-observation integration wires it; no platform primitive closes it for regular files.
2. Hard-linked files lose their link on save; xattrs and ACLs of the replaced file do not survive atomic replacement; setuid, setgid and sticky bits are stripped (REQ-WR-110).
3. Orphaned staging files of crashed sessions are never auto-cleaned; they are dot-hidden and caller-owned. A workspace opened in Git will show them as untracked until deleted — visible, but never mistaken for real content, and deletion is always safe.
4. Windows-only behaviors (sharing-violation retries, chmod fidelity) are unverified here; the suite runs on Darwin.
5. `avatar.go` cache writes remain non-atomic, documented as out of lane scope (display cache, not user content).
6. Backup copies of corrupted configurations (`config.json.broken-<timestamp>`) accumulate forever: every corrupted launch adds one, and nothing removes them, because each may hold the only copy of settings the user never repaired. They are config-directory-sized and safe to delete by hand — documented here rather than rotated, since silently deleting backups is the worse failure.

## The independent-verification fix round

An independent adversarial verification (branch `verify-lane-c`, report at `docs/specs/conformance/verify-lane-c.md` there) judged the lane needs-fix and proved each finding with a reproduction. The fixes, all in this lane's ownership:

| Finding | Resolution |
|---|---|
| F-1: zero-value repairs silently overwritten by preserved invalid values | Write-back re-contracted by representability — see REQ-CFG-070 above. Regression: `TestZeroValueResetSticksOnWriteBack`. |
| F-2: failed backup left the original unprotected against the next save | The REQ-CFG-040 overwrite gate is enforced — see above. Regression: `TestFailedBackupBlocksOverwriteUntilBackupSucceeds`. |
| REQ-WR-080 premise factually false (rename failures are not all permanent) | Behavior unchanged; the reasoning corrected to cost and uncertainty — see REQ-WR-080 above. |
| F-5: session state raced under concurrent use, threading contract undocumented | Sessions now serialize internally and the sharing contract is documented — see REQ-WR-040. `TestSessionSharedAcrossGoroutines` is race-clean where the verifier's opt-in probe reported the race. |
| F-3: explicit nulls silently erased | Deliberate normalization, now documented: null reads as unset and write-back omits it, carrying the same information. `TestNullReadsAsDefaultAndNormalizesOnWriteBack`. |
| F-4: wrongly-typed version silently normalized | Fixed by the same representability rule: a version this build cannot read as a number is not representable, so it is preserved. `TestWronglyTypedVersionStaysPreservedOnWriteBack`. |
| F-6: setid/sticky bits stripped; config mode 0640→0600 | The bit stripping is real and now documented in the package comment and REQ-WR-110. The config-mode claim does not reproduce: an existing 0640 config keeps 0640 through `WriteFilePerm(…, 0600, …)` because `Begin` copies the replaced file's permissions; 0600 applies only to newly created files, as documented. |
| F-7: panic in the write callback leaks the staging fd | Fixed: `WriteFile`'s deferred `Abort` closes the handle and removes staging before the panic propagates. `TestPanicInWriteCallbackCleansUp`. |
| F-8: backup files accumulate forever | Documented as deliberate — see known gaps, item 6. Silently deleting backups that may hold the only copy of user settings is the worse failure; the files are small and hand-deletable. |

The verification's cross-lane conclusion is acted on without pre-empting the integration: `atomicfile` gained `CommitIf` (best-effort condition evaluated immediately before the rename, documented as the REQ-COND-070 degradation) and `CommitIfAbsent` (link-based, truly atomic create-if-absent). Neither is wired into the save paths — that belongs to the integration phase with the file-observation lane, which can now publish conditionally instead of composing stat-and-write outside the session, the shape REQ-COND-050 forbids advertising as conditional. The verifier's torn-content strengthening was adopted as `TestConcurrentReadersNeverSeeTornContent`.
